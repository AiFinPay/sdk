# B2BSplitter v1.3 — Protocol Route Registry

## Routes

v1.3 introduced protocol routes with immutable fee splits at construction.

| Route | Treasury Bps | IP Creator Bps | Description |
|-------|--------------|----------------|-------------|
| `merchant-aifp1` | 100 (1%) | 0 | AIFP-1 gross-inclusive settlement. Agent pays quoted gross; treasury receives 1%, merchant receives 99%. |
| `agent-x402` | 0 | 0 | AIFP-2/x402 negotiation. Provider receives 100% of quoted price; AiFinPay fee is 0%. |

## Deployment lookup

Read [deployments.json](deployments.json) for addresses, assets, runtime hashes,
governance and settlement metadata. Select records using
`chainId` and `_route`, never address alone. The same address can occur on
different chains or routes with different economics.

Do not use a chain-only lookup to select between v1.3 routes:
[AifinpayRegistry](../../../../src/registry.ts) keys its EVM map by chain ID.
The SDK's [route resolution code](../../../../../node/src/splitterRoutes.ts)
defines route-specific lookup and policy checks.

## Verification and provenance

Inspect the actual selected registry record and the consumed route table's
`validFrom`/`validUntil` policy before settlement. Compare deployed runtime code,
mutable owner/treasury and route economics with the expected values, and obtain
fresh backend receipt-verification and end-to-end settlement evidence.

See the [verification checklist](../../INDEX.md). Registry metadata and policy
dates do not establish current availability; settlement-disabled or
out-of-window routes must not settle.

Read `source`, `sourceArtifact` and `generatedAt` in the JSON for recorded
provenance. This route snapshot is not regenerated by the
[grabber](../../../../src/grabber.ts). Downstream generation is implemented in
[generate-splitter-routes.mjs](../../../../../node/scripts/generate-splitter-routes.mjs);
from `node/`, `npm run registry:check` checks consistency with the installed
deployment package, not live verification.
