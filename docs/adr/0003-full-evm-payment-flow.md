# ADR 0003 — Extend the existing EVM v1.4 payment kernel

Date: 2026-10-04. Traceability: FULL-PAYMENT-FLOW-20261004.
Status: architecture approach approved by the user; additive quote wire agreed with root, backend owner and architecture reviewer.

The user requires complete agent payment flow for every existing supported network. This SDK change reuses the existing signed v1.4 EVM executor, receipt verification, owner budgets and durable recovery. It does not introduce another runtime architecture or dependencies. The initial source scope is the nine current EVM mainnets: Polygon, Base, Optimism, Arbitrum, Avalanche, BNB, Unichain, XRPL EVM and Robinhood. Amoy remains a low-level test executor; historical BOT is not silently mapped to Robinhood. Non-EVM families need their actual verified deployment/receipt/signing prerequisites before client support can be claimed.

Caller configuration authorizes the payment chain and asset. A merchant quote never selects the wallet RPC or expands the owner's authorization. Independently reviewed metadata supplies native denomination, pinned-token decimals and gas policy; deployed contract/address/signer/code pins continue to come from the unchanged generated registry. Quote amount and settlement aliases retain six-decimal USD micro-units. Optional POST settlement_chain requires explicit merchant authorization. Additive token_settlement carries asset, token, decimals, total_units, merchant_units, protocol_fee_units, creator_units and settlement_semantics=gross-inclusive. Signed gross, approval and token total are equal to exact USDmicro multiplied by10^(decimals-6). Legs use the token-unit100/0 split, not scaled rounded USD legs. Missing metadata is accepted only for independently pinned six-decimal tokens. Profiles remain mutable under the accepted v1.4 trust model: current profiles are checked before broadcast; receipt/recovery policy is unchanged and this metadata does not make fees immutable.

OP fee models include data/operator estimates in the same owner budget as approval and settlement. Nitro estimates already include the parent-data component; no Base-style extra fee is added. RPC errors, missing fees, token metadata disagreements, unknown chains and unsupported families refuse before signing. All existing runtime/profile/payer/nonce/expiry/signature, SSRF, receipt and quota controls remain in force.

Independent review reproduced a Python check/record race across two instances sharing a $1 daily cap: both could authorize $0.60 before either recorded spending. Python2.4 therefore reserves under a fresh-read kernel file lock before approval/signing, using an additive version2 reservation schema beside exact migrated legacy confirmed entries. Ledger and prepared transaction journal writes use owner-only temporary files, fsync, atomic replace and directory fsync. Unknown broadcasts do not expire. Confirmed execution records one reservation-keyed debit using the existing conservative validated USD valuation; the purchase guard survives receipt/HTTP failures until verified recovery. Recovery binds payer, API/issuer, merchant/scope/resource/mode, original chain/asset/token/gross/quote and transaction hash derived from signed bytes. The purchase key deliberately excludes chain/asset while the exact reservation binding includes them: switching rails cannot duplicate unresolved access. Only proven nonbroadcast or reverted settlement releases gross; gas remains separately bounded. Confirmed debits follow the24-hour window, and recovery is idempotent. Reconciliation-only ledger views cannot authorize a new payment. Corrupt/unknown state or unavailable OS locking fails closed. These guarantees cover one shared local journal filesystem, not multiple hosts; older Python versions must not read a2.4 ledger with pending reservations, because they ignore the additive pending state.

Verified receipt symbols follow the existing backend uppercase convention (USDe→USDE, USDC.e→USDC.E). Only the already verified JWT asset is compared after uppercase normalization to the independently authorized canonical asset; the response must equal its signed claim exactly. Quote/call/token metadata and wallet authorization retain their exact canonical symbols and address/decimal/chain bindings.

The approved scope also hardens Node's public file ledger: corrupt/unreadable state no longer resets spending, unresolved reservations no longer expire, and aged locks are never stolen. File locks have bounded fail-closed contention and writes are private, atomic and fsynced. Additive prepare/assertRecovery/complete hooks attach exact original purchase binding and signed-byte hash before broadcast; capped v1.4 custom adapters lacking them refuse before payment. Unknown outcomes preserve the reservation; confirmed-but-unreceipted purchases preserve the access guard. Completion records a debit once and retains reconciliation identity after 24 hours without counting old confirmed spend. Historical bound identities grow and must not be truncated while recovery remains possible. Existing array entries migrate without changing their amounts. Old SDK releases must not operate on pending 2.4 state until transactions have been reconciled.

MCP now persists prepared.chain rather than relying on the quote's rail plus the low-level Polygon default. Legacy missing-chain state can only adopt the independently configured owner chain after actual signed transaction bytes prove chain ID, payer, pinned target, exact calldata/value and token/approval. Insufficient evidence fails closed and requires manual receipt reconciliation; it never resubmits payment. Recovery validation permits an expired signing deadline and deliberately performs no new runtime/profile/RPC check against an already broadcast transaction. Offline tests exercise real signed Base/Robinhood transactions, real wallet receipt authorization and real Ed25519 receipt verification through the public SDK.

Release is coordinated: Node/Python2.4.0, MCP2.6.0 and canonical sibling skill2.7.0 describe the prepared cohort. Skill publication baselines are explicitly dated; an exact release target does not claim publication or production activation. Same-commit source-cohort CI builds and packs the actual Node candidate for MCP. Real publication of agent2.4.0 and canonical skill2.7.0, a published MCP dependency/lock refresh and standalone registry CI remain release prerequisites. The old locked registry inputs are retained until publication, with no invented resolutions. Hosted MCP CI may remain pending that real skill input while local source-cohort evidence is recorded separately. Version gates remain meaningful rather than being disabled to hide unpublished exports.

This is High-risk payment code with a 20% autonomy cap. The user's instruction authorizes local implementation of the existing architecture. Independent QA/security/architecture review and human approval remain mandatory before a merge or release; hosted CI, per-network deployment-state checks and actual paid acceptance remain separate from offline tests. No contract source, fees, route profiles, settlement flags or production activation is part of this SDK change.
